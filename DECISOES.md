## Decisões assumidas
1. O pedido não especifica as tabelas a serem criadas, então a escolha foi de fazer 3 tabelas principais que representariam os itens de interesse da aplicação: ALUNO, EQUIPAMENTO, EMPRÉSTIMO, com  seus respectivos campos. Cada tabela foi pensada com os relacionamentos de chaves primárias e estrangeiras, regras envolvendo as colunas e limitações do próprio banco, uma alteração que fosse em uma só coluna de uma tabela impacta todos os registros gerados anteriormente com a tabela desatualizada e também os relacionamentos com as outras tabelas do sistema. As funções de CRUD das tabelas são basicamente inutilizadas e as funções da tabela empréstimo não tem mais referência das tabelas que precisa acessar de forma a executar as operações e gerar os registros sobre as transações.
2. Usando o sqlite, a ferramenta de gerar código decidiu usar INTEGER ao invés de INT nas declarações das tabelas, pois, segundo, ela e checando posteriormente, o INTEGER gera o comportamento de uma PRIMARY KEY por padrão, onde o INT não. Assumindo que o comportamento esperado era o de uma PK, a decisão foi bem acertada. Caso fosse decidido por usar outra declaração que não essa, a configuração deveria cumprir com as regras para utilizar uma PK: única, aceita apenas inteiros, sequencial, tamanho fixo e poderia bagunçar o código já gerado anteriormente. 
3. O pedido não especifica um menu específico, então inicialmente, assumindo que é preciso apenas inserir e exibir os dados, foi criado um menu interativo simples, apenas para dar ao usuário o que os inputs simples permitem. O menu é a forma com que se interage com a aplicação, então uma mudança no que o cliente quer que seja visível ao usuário, ou até se vão haver diferentes níveis de acesso, podem variar de um impacto irrisório sentido apenas numa mudança de botão até um nível altíssimo, como diferenciar menus nos acessos a diferentes usuários.
4. Na hora de fazer o CRUD, foi feito uma tentativa de criar algo o mais simples possível para melhor entendimento do código. Foram feitas as alterações sempre em busca de usar o ID como base para as alterações do CRUD, como as funções de exibir via ID, atualizar e deletar. Assim, o CRUD é feito com base no que é mais certo na hora de buscar e alterar dados na aplicação. Uma mudança apenas em como é pedido que um dado seja alterado impacta em diferentes partes do sistema porque pode-se mudar a forma em que se exibe os dados quando são pedidos, como se altera dados que são enviados e toda a parte da interação do usuário com as partes mais internas do sistema. Essas alterações incluem as funções de cada tabela e as regras de negócio implementadas, como os empréstimos a pessoas que estão com pendências e os registros a serem gerados para cada tipo de operação no sistema.
5. Para delimitar as regras de negócio é primeiro preciso definir o que é o empréstimo. O empréstimo é um aluno que pega um item e que se não devolver no prazo especificado fica como "pendente". Essa é a coluna vertebral do sistema, caso seja pedido uma alteração nas colunas, como não utilizar o ID, ou não registrar infrações que já estiverem resolvidas, com o item devolvido, ou um indicador para um número de infrações de um aluno são um golpe muito forte no design do sistema quase como um todo. Uma alteração na regra de negócio impacta nessa tabela e também reverbera para as outras partes que dependem dela.
6. O pedido não especifica um prazo para devolução, ele foi decidido arbitrariamente como 7 dias por questões de facilitar a criação das tabelas e código da aplicação. A mudança na contagem de dias impactaria na alteração de regra no código e não bagunçaria o código intrinsecamente, no entanto geraria um pequeno caos entre os resultados esperados.
7. O pedido não especifica nenhuma punição detalhada sobre o empréstimo atrasado, então o decidido foi 7 dias em acordo com o prazo de devolução para manter a consistência entre a entidade e as regras. A alteração para outro número de dia teria implicações semelhantes às da mudança no prazo de devolução.
8. O pedido não especifica o que deve estar no relatório exatamente, então foi assumido que as métricas importantes seriam listar todos os empréstimos, os empréstimos ativos, os atrasos e os alunos com pendências. Qualquer alteração implicaria em mudança nas funções e geração do relatório como um todo, além das funções de apoio para suportar a criação do relatório.
9. O pedido não especifica se testes devem ser inclusos como parte do programa. Foi assumido que para a parte mais essencial do negócio, testes deveriam estar presentes para atestar as partes mais importantes da regra de negócio. A decisão foi de incluir testes nas funções mais importantes do sistema, como a de fazer empréstimos e verificar pendências. Uma mudança nesse pedido não teria um impacto direto no funcionamento da aplicação, no entanto, não daria tanta segurança de quem está vendo o sistema de fora de entender o seu funcionamento e se tudo está sendo atendido como especificado. Para ressaltar, são apenas testes com prints demonstrativos para melhor entendimento de como funcionam as regras implementadas.
10. O pedido não especifica se todos os empréstimos, independente do histórico do aluno, devem ser armazenados. Foi assumido que sim para fins de padronização, no entanto, uma alteração de regra impactaria na criação de outra tabela e poderia criar pontos cegos para o caso de, por exemplo, um infrator recorrente tivesse que receber uma punição mais severa.
11. O pedido não fala de equipamento perdido ou de punições diferentes. Foi assumido que todo equipamento vai ser devolvido em algum momento, da mesma forma que foi entregue ao aluno e que nenhuma infração implica outra, então alunos com infrações recorrentes, por exemplo, recebem a mesma punição que alunos que cometem poucas infrações.
12. Não se fala do formato do relatório, então foi decidido que ele seria na forma de uma função dentro do próprio sistema. Caso o cliente escolhesse fazer em uma outra formatação ou exportar de outra maneira, isso iria impactar na geração e no menu principal da aplicação.
13. O sistema não tem tratamento para uma dupla execução ou duplo acesso para fins de simplificação. Essa questão não foi ressaltada no pedido, mas foi assumido que apenas uma pessoa vai usar o sistema por vez e fará um empréstimo de cada vez, como uma bibliotecária emprestando um livro de cada vez a apenas um aluno. Se isso fosse ressaltado no pedido, implicaria em mudanças na tabela e no código para garantir uma precisão de tempo nas entregas e pedidos e também tratamento de erro para casos em que houvesse esse tipo de ocorrência.

## Perguntas ao cliente
1. *Quais são as regras de negócio detalhadamente(i.e. tempo máximo de devolução, tipo de punição para infratores, punição severa para infratores recorrentes, etc.)?* Os detalhamentos da regra de negócio definem todo o desenvolvimento da aplicação, sem elas não é possível definir o que fazer e nem o que entregar. O cliente quer uma aplicação mais robusta internamente? Quer um design profissional e um back-end mais simplório? Quer o relatório em texto ou planilha e pdf? Todas essas e mil e uma outras decisões impactam diretamente em todo o contexto do fluxo de desenvolvimento. Se a resposta para qualquer uma dessas perguntas fosse diferente do que já foi proposto no design atual isso implicaria em redesenhar as tabelas para atender aos requisitos, reescrever boa parte do código para estar alinhado com as novas demandas e criar novo código que atenda ao que nem foi proposto inicialmente no desenvolvimento do projeto.
2. *Haveria auditoria de terceiros?* Por mais que um cliente peça um sistema, nunca se sabe se ele é a ponta final daquele pedido. Por exemplo, uma escola pode pedir esse sistema de controle dos equipamentos, mas quem realmente vai utilizar é a equipe responsável pelos laboratórios. O cliente pode ser só um intermediário entre o desenvolvedor e o usuário, então existe um ruído entre a comunicação dos dois lados que passam por esse terceiro. Saber de quem e para quem se faz o sistema impacta nas decisões, no tempo entre perguntas e respostas e as entregas pedidas pelo cliente final e do intermediário. As funcionalidades poderiam se adequar aos pedidos mais específico daquele departamento, por exemplo: "Use as credenciais do laboratório, não as matrículas na escola", "O cadastro de equipamentos deve seguir uma base de dados já existente e não utilizar uma nova", dentre outras.
3. *O código tem que ser mantido ou ele é um 'tapa-buraco' para um problema temporário?* É claro que nunca pode-se prever o futuro, mas com base nos problemas do presente pode-se desenhar uma ideia de como vai ser o futuro. A proposta não é clara quanto à logevidade do sistema ou do problema. Se o sistema for apenas algo que não vai se manter por muito tempo, que vai ser resolvido de outra maneira, mas que tem que ter algo que segure o seu lugar enquanto ainda não está pronto, é melhor poupar esforços e fazer algo que apenas mantenha as coisas em ordem enquanto se espera algo mais robusto. Se for o contrário, é melhor tentar fazer uma arquitetura forte, entender o desenrolar de problemas no futuro e se planejar para escalonar de forma mais agressiva, dessa forma colocando mais esforço tanto no planejamento quanto na execução. Uma previsão e detalhamento do problema pela área de negócio impacta diretamente o desenvolvimento, planejamento e esforço colocado na resolução daquele problema. As decisões como registro de auditoria, que aqui foram ignoradas, poderiam ser extramamente relevantes em um sistema permanente e que deve ser monitorado, decisões de negócio como punição para infratores recorrentes são bem mais impactantes em um sistema de funcionamento continuo do que em um sistema temporário.

## Critérios de aceite
1. Criar um empréstimo com um aluno que não tem nenhuma pendência gera um registro ativo de empréstimo.
2. Criar um empréstimo com um aluno que possui alguma pendência retorna com erro sobre a pendência e não gera resgistro.
3. Criar um empréstimo com um item que já está emprestado a outra pessoa retorna erro e não gera registro.

## Decisão da ferramenta de IA
A principal decisão tomada por ele foi na função de deletar o histórico de alguém sem registro de auditoria. Assumindo perfeitas condições para os usuários e que o cliente consegue monitorar por conta própria os usuários do sistema, isso pode não ser de tanto impacto, no entanto um cliente que queira um escopo maior ou não tenha recursos para fiscalizar os usuários do sistema podem pedir uma alteração ou remoção dessa função para garantir um funcionamento mais completo do sistema.
